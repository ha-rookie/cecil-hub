AI-DRIVEN DEVELOPMENT — PRACTICE LOG

Every app I build with AI
changes the way
I build software.

At first, I was not sure how far AI should be used in development. After building several apps, some things became clearer: where AI helps, where a person should still check the work, and which rules were simply too much. This page keeps that record.

Build → Check → Review → Change the next project

WHAT IS ON THIS PAGE

Not a finished method.
A record of what changed.

This is not a general guide to AI-driven development. It focuses on what happened while building real apps, what caused trouble, and what changed afterward. It also leaves enough detail for managers and customers to see how the work is checked.

01 / ABOUT THIS PAGE

At first, I did not know how far
AI should be used in development.

I started with code generation, then gradually used AI for design, issues, tests, and documentation. At the same time, I found places where a person should still check the work, and places where I had added too many checks. This page keeps that unfinished process visible.

03 / WHERE PEOPLE STILL CHECK

Some things are easier to automate.
Some are still better checked by a person.

More human checkpoints do not automatically mean more safety. I try to keep human checks where the impact is larger, and use mechanical checks elsewhere.

ProductionImportant changes are checked before release
Large scope changesA person decides when the purpose or user impact changes
Permissions / SecuritySecrets, authentication, and data operations get extra attention
Actual UIEven after CI passes, the real app is still checked
04 / WHAT DID NOT WORK

The problems were not always
about the model itself.

I added too many human checkpoints, made some test conditions too strict, and sometimes lost the current state when a conversation was restarted. Using AI also made sloppy handoffs and unclear checks easier to notice.

TOO MANY CHECKS

Human checkpoints became a bottleneck

Safe, but development stopped too often.

TOO STRICT

Some tests were heavier than the app needed

Small apps inherited checks that did not always add enough value.

UNCLEAR OWNERSHIP

Images and files caused rework

It helped to decide in advance what the AI does and what the person does.

LOST CONTEXT

Restarting a conversation could lose the current state

Now I return to the Issue, Branch, PR, and main branch first.

05 / WHAT CHANGED AFTERWARD

The way I develop changed
with each app.

The current process did not exist from day one. Issues, pull requests, design docs, CI, and production checks were added when they became necessary. The mahjong score app now adds authentication and a database, which brings the process closer to business-system concerns.

FIRST

Use AI to write code

Start by testing how much could actually be built.

NEXT

Add Issue / PR / design

Keep track of the change and why it exists.

THEN

Add CI and production checks

Do not stop at “it was generated.” Keep evidence of what was checked.

NOW

Try authentication and D1

Auth, API, concurrency, logging, performance, and D1 query design are being tested.

06 / RULES I ADDED AND REMOVED

A failure can add a rule.
That rule does not have to stay forever.

A check that was useful once may stop being useful when the model, tool, or project changes. I review whether to keep it, make it lighter, or remove it.

Something feels wrong→Temporary rule→Use it→See the result→Keep / lighten / remove→Next project

Examples: too many human checkpoints / strict test conditions / upload ownership / context recovery / quota limits.

07 / HOW I CHECK THE WORK

Not “it should be fine.”
Leave something that can be checked.

Whether AI is used or not, I do not want the basis for “checked” to disappear. Where it matters, I keep Issues, PRs, CI results, Preview checks, and production verification.
