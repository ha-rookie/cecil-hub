AI-DRIVEN DEVELOPMENT PRACTICE LOG

Each app changed
the way I develop
with AI.

At first, I was not sure where AI should be used in development. After building several apps, it became clearer where AI helps, where people should still check, and where I had added too many checks. This page keeps that evolving record.

BUILD → CHECK → REVIEW → CHANGE THE NEXT PROJECT

WHAT IS ON THIS PAGE

What I actually tried,
and what changed.

This is not a general guide to AI-driven development. It is a record of methods used in real app development, what failed, and what changed afterward.

01 / ABOUT THIS PAGE

Using AI changed more than coding.

I started by asking AI to write code. Over time, I also used it for design, Issues, tests, and documentation. As that scope grew, it became clearer where human checks still matter—and where I had added more checks than needed. This page keeps that process visible.

02 / WHERE AI IS USED

AI is now used beyond writing code.

It helps organize requirements, propose designs, split work into Issues, implement changes, write tests, and summarize changes. But not every step is treated the same way.

03 / WHERE PEOPLE STILL CHECK

People still check the parts with larger impact.

More human checkpoints do not automatically make a process safer. Today, people mainly review changes that affect purpose, users, production, authentication, permissions, or the actual user experience.

ProductionImportant changes are reviewed before release
SpecificationPeople decide when the purpose or user impact changes
Auth / permissionsSecrets, authentication, and data operations get extra checks
Real screensPassing CI is not enough; production and devices are checked too
04 / WHAT DID NOT WORK

Some problems had little to do with model capability.

I added too many human checkpoints, made test conditions too strict, and sometimes lost the current state when resuming a long conversation. Using AI exposed weak handoffs and weak verification just as much as it exposed AI limitations.

TOO MANY CHECKS

There were too many places to stop

The process became heavy even when the risk was small.

TOO STRICT

Tests grew beyond what small apps needed

More checks did not always mean more useful confidence.

UNCLEAR HANDOFF

Images and files caused rework

The human and AI responsibilities had not been decided early enough.

LOST CONTEXT

Resuming later made the current state unclear

Now Issue, Branch, PR, and main are checked before resuming.

05 / WHAT CHANGED AFTERWARD

I add what becomes necessary and remove what becomes too heavy.

The current process did not exist from the beginning. Issues, PRs, design docs, CI, and production checks were added when they became useful. Checks are also reduced when they no longer fit the size or risk of the project.

FIRST

Ask AI to write code

Start by seeing what could actually be built.

NEXT

Expand into Issues, PRs, and design

Keep the change unit and the reason for the work visible.

LATER

Add CI and production checks

Keep evidence of what was actually checked.

REVIEW

Reduce checks that became too heavy

Match verification to project size and risk.

NOW

Test auth and DB work in the Mahjong app

Auth, D1, API, concurrency, logging, and performance are now in scope.

06 / RECORDS AND REAL FILES

I try to leave enough evidence to see what was checked.

Whether AI is involved or not, I do not want “checked” to mean something vague. Issues, PRs, CI results, and production checks are kept where needed, and public design or process documents link to the actual files.

07 / THINGS I WATCH OVERSEAS

I watch overseas work only when it may change how we build.

This section is not for listing new tools. I only want to keep items where a primary source is available and where the idea caused a concrete change—or a concrete review—in the CECIL process.

REVIEWING

Can long work resume cleanly?

Check whether Issue and PR evidence are enough to recover the current state after a conversation changes.

REVIEWING

Have too many rules accumulated?

Revisit older restrictions when models and tools change.

REVIEWING

Are we checking production correctness?

Focus on whether the real application works, not only whether code was generated.

The public version will only keep items that have a primary source, a review date, and a concrete CECIL change or review attached.
