AI駆動開発 実践記録

AIとアプリを作るたびに、
開発のやり方そのものが
変わっていった。

最初は、AIを開発のどこまで使っていいのか分からなかった。何個かアプリを作るうちに、AIで進めやすいところ、人が確認した方がいいところ、逆にやりすぎだったルールが少しずつ見えてきた。その変化を残しています。

作る → 確かめる → 振り返る → 次で変える

このページに書いていること

完成したやり方ではなく、
今まで変えてきたこと。

AI駆動開発の一般論をまとめるのではなく、実際に作って、困って、変えたことを中心にしています。管理する側や依頼する側が気になるところも、同じ流れの中で確認できるようにします。

01 / このページについて

最初は、AIを開発のどこまで
使っていいのか分からなかった。

コードを書いてもらうところから始めて、設計、Issue、テスト、ドキュメントまで使う範囲が広がりました。その一方で、「ここは人が見た方がいい」「これは確認を増やしすぎた」ということも出てきました。このページでは、その途中経過をそのまま残します。

開発する人どこでAIを使うと進めやすいかが分かる
管理する人どこで人が確認しているか、変更履歴が残っているかを見られる
依頼する人AIを使っていても、何を確認してから本番へ出しているかが分かる
02 / AIを使っているところ

今は、コードを書くところだけでは
なくなっています。

要件を整理する、設計案を出す、Issueへ分ける、実装する、テストを書く、変更内容をまとめる。AIを使う場所は少しずつ増えました。ただし、全部を同じように扱ってはいません。

03 / 人が確認しているところ

自動で進めた方が楽なところと、
人が見た方がいいところを分けています。

人の確認を増やせば安全になるわけでもありません。今は、影響が大きいところを中心に人が確認し、それ以外はできるだけ機械的に確かめるようにしています。

本番反映重要な変更は、人が内容を確認してから進める
大きな仕様変更目的や利用者への影響が変わる時は、人が判断する
権限・SecuritySecret、認証、Data操作は確認点を増やす
実際の画面CIが通っていても、本番や実機で見る
04 / うまくいかなかったこと

うまくいかなかったのは、
AIの性能だけが理由ではなかった。

人の確認を増やしすぎたり、テスト条件を厳しくしすぎたり、途中から会話を再開した時に状態がずれたりしました。AIを使うほど、仕事の渡し方や確認方法の雑さも見えやすくなりました。

確認しすぎた

人が止める場所が多すぎた

安全ではあるが、毎回止まって開発が重くなった。

厳しくしすぎた

テスト条件を増やしすぎた

小さなアプリに必要以上の確認を持ち込んだ。

分担が曖昧だった

画像やFileの扱いで手戻りした

AIがやること、人がやることを先に決める必要があった。

途中でずれた

会話をまたぐと状態が分からなくなった

Issue、Branch、PR、mainを見て再開するように変えた。

05 / そこから変えたこと

アプリを作るたびに、
開発のやり方も変えてきました。

最初から今の形だったわけではありません。必要になった時にIssue、PR、設計書、CI、本番確認を足してきました。三麻スコアでは認証やDBまで入り、業務システムに近い確認も増えています。

最初

AIにコードを書いてもらう

まずは、どこまで作れるかを試した。

次

Issue / PR / 設計へ広げる

変更単位と、何を作っているかを残すようにした。

その後

CIと本番確認を増やす

「作れた」だけで終わらず、確認した記録を残すようにした。

今

三麻スコアで認証・DBまで試す

Auth、D1、API、排他、Logging、Performanceを確認中。

06 / 増やしたルール、減らしたルール

失敗したらルールを増やす。
でも、増やしたままにはしない。

一度必要だった確認でも、AIやTool、Projectの大きさが変われば不要になることがあります。残す、軽くする、やめるを定期的に見直します。

気になること→仮のルール→実際に使う→結果を見る→残す / 軽くする / やめる→次の開発

例：Human checkpoint過多 / Test条件過多 / Upload分担 / Context復帰 / Quota制約。
